# Crawling and sharing policy

The site should be **findable** and **shareable**, and should not hand anyone the database.
Those two goals are compatible only if you separate *indexing* from *bulk collection*: search
engines get pages, nobody gets a file.

## What is in place

| Layer | Where | What it does |
| --- | --- | --- |
| Crawler policy | `public/robots.txt` | Googlebot, Bingbot, DuckDuckBot, Applebot and the link unfurlers may crawl everything except the dataset and `/x/`. AI-training and SEO-tool crawlers are refused by name. Every unnamed crawler is refused. |
| Header belt | `public/_headers` | `x-robots-tag: noindex, nofollow, noarchive` on `data.json`, `games.json`, `scores.json`, `rankings*.json`, `franchises.json`, `history-results.json`. A bot that ignores robots still cannot get these indexed. |
| Real URLs | `src/lib/app.tsx`, `netlify.toml` | Paths, not hashes: `/player/cj-kirst` is a URL a crawler or a chat client can ask for. Old `#/player/…` links are read and rewritten on arrival. `vite.config.ts` base is `/` — with `./` the bundle 404s on a deep path. |
| Per-page head | `netlify/functions/meta.ts` | Answers `/player/*`, `/team/*`, `/league/*` with the app shell plus that entity's `<title>`, description, canonical, Open Graph/Twitter card and JSON-LD (`Person` / `SportsTeam` / `SportsOrganization`). Unknown slug → real 404, no soft 404. |
| Share image | `public/og.png` | 1200×630 card used by every entity until per-entity images exist. |
| Sitemap | `scripts/gen-sitemap.mjs` → `/sitemap.xml` | 22,443 URLs, regenerated by `npm run build`. **Not referenced in robots.txt** — see below. |
| Canary | `netlify/functions/meta.ts` (`/x/*`) | Disallowed in robots.txt, linked from nowhere. A hit is a crawler ignoring rules. Each hit is logged as one JSON line. |

## Why the meta function carries no data

`/player/cj-kirst` returns a name, a club, a position and one stat line — the text of the card.
Season tables, game logs and career totals are **not** in the HTML; they arrive only when the app
boots and fetches `data.json`, which robots.txt refuses and the header marks noindex. So an indexed
page is a business card, and the database still costs a blocked request.

## What still has to be done by hand (once)

1. **Google Search Console** — add the domain, verify it (DNS TXT is easiest), then submit
   `https://laxdb.netlify.app/sitemap.xml`. This is the step that makes 22k pages findable, and the
   reason the sitemap is not advertised in robots.txt: submit it there, not to every crawler.
2. **Bing Webmaster Tools** — same sitemap URL; it feeds DuckDuckGo and ChatGPT's search too.
3. **Rate limiting** (optional but recommended) — Netlify's free plan has no WAF or per-IP limits.
   Putting Cloudflare in front (free plan) gives bot-fight mode plus one rate-limit rule for
   `/data.json` and `/games.json`, which is the only remaining cheap path to the bulk file. That is
   a DNS change, so it is a decision, not a code change.

## Checking it afterwards

```bash
curl -s https://laxdb.netlify.app/player/cj-kirst | grep -E "<title>|og:title|canonical"
curl -sI https://laxdb.netlify.app/data.json | grep -i x-robots-tag
curl -s https://laxdb.netlify.app/robots.txt | head -20
curl -s https://laxdb.netlify.app/sitemap.xml | grep -c "<url>"
curl -s -o /dev/null -w '%{http_code}\n' https://laxdb.netlify.app/player/not-a-player   # 404
```

Canary hits: Netlify → Functions → `meta` → logs, each line a JSON object with `canary`, `ua`,
`ip`, `referer`, `at`. Known-good crawlers never appear there; anything that does is worth blocking.

## Known limits

- robots.txt binds the crawlers that play fair (Google, Bing, OpenAI, Anthropic, Common Crawl) and
  not the ones that do not. It is a policy statement, not an access control.
- The dataset is a public file that the browser must fetch, so anyone with a browser can still read
  it. The goal is cost and detectability, not secrecy: one request used to yield 18 MB; now it takes
  a rate-limited fetch plus an ignore of robots.txt, and it leaves a log line.
- `#/…` links still work, but only the path form has a canonical URL. Anything printed or posted
  from now on should use `/player/…`.
